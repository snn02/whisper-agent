# Правила разработки

## Состояние и ближайшие шаги

Готовы: поиск медиа и защита путей, Python-обработчик, CUDA-образ, Node CLI и MCP, журнал JSONL, Windows-установщик и документация. Работа зафиксирована по этапам на `main`, начиная с коммита `f9f0514`. Модульные тесты проходят; реальная сборка образа, установка на Windows, распознавание русской записи и подключение приложений ещё требуют проверки вне песочницы.

Далее: проверить установщик PowerShell на Windows, собрать образ и выполнить GPU smoke test, распознать короткую русскую запись, проверить журнал и удаление контейнера, затем проверить доступность инструмента в Codex, Claude Code, локальном Cowork и OpenCode. Ошибки, обнаруженные в этих проверках, исправлять в проекте до выпуска.

## Изменения и проверки

- Сохраняйте общую логику в `src/core.mjs`; CLI и MCP только преобразуют аргументы и результаты. Обработку файлов и вызов Whisper держите в `container/worker.py`.
- Docker запускайте без shell. Проект монтируйте только для чтения, результат отдельно для записи, кэш моделей — в именованном томе. Не вводите скрытый CPU fallback и не перезаписывайте результаты молча.
- Журнал содержит метаданные запуска, имена файлов, длительности и ошибки, но никогда полный текст. Сохраняйте текст только в результирующих файлах.
- Для исправления дефекта сначала воспроизведите его минимальной проверкой. Для нового поведения пишите тест, если он проверяет риск на границе (пути, Docker argv, формат MCP, перезапись, частичный сбой). Не добавляйте тесты, повторяющие реализацию.
- После изменения Python запускайте `python3 -m unittest discover -s tests -p 'test_worker.py' -q`; после Node — `npm test`. Перед коммитом выполняйте `git diff --check`. Сборка Docker, GPU smoke и PowerShell-парсер — отдельные ворота на Windows; модульные тесты их не заменяют.
- Сообщения коммитов: короткий повелительный глагол на английском и предмет изменения, как `Add CUDA Whisper Docker image`. Один коммит — один проверяемый этап. Не включайте модели, медиа, результаты, журналы и `node_modules`.

## Superpowers

Применяйте только процедуры, которые помогают конкретному изменению. Для нового сложного поведения сначала согласуйте короткий дизайн и план; для воспроизводимого дефекта используйте систематическую диагностику; перед завершением проверьте фактический результат. Для небольшой правки текста или конфигурации достаточно чтения, изменения и одной уместной проверки. Не создавайте дополнительный план, worktree, субагентов или серию тестовых прогонов только ради процедуры. Явные инструкции пользователя имеют приоритет.

## Нумерация версий

Используем SemVer `MAJOR.MINOR.PATCH`. Пока версия `0.x`, несовместимое изменение интерфейса CLI/MCP или формата результатов повышает `MINOR`; совместимая новая возможность тоже повышает `MINOR`; исправление без новой возможности повышает `PATCH`. `1.0.0` — отдельное решение после подтверждённой работы на основной Windows-платформе. Предварительные версии: `0.2.0-rc.1`, `0.2.0-rc.2`. Версия в `package.json`, `package-lock.json` и манифесте Claude-плагина должна совпадать; MCP читает её из `package.json`. Тег Docker с PyTorch/CUDA (`torch2.13-cu132`) обозначает стек образа и не является версией продукта.

## Релизы
<!-- relizer: v1 -->

| Параметр | Правило |
|---|---|
| Версия | SemVer по разделу выше; текущая `0.2.0` ещё не выпускалась |
| Файлы версии | `package.json`, `package-lock.json`, `integrations/claude-plugin/.claude-plugin/plugin.json` |
| Метка | Аннотированная `v{version}` или `v{version}-rc.{n}` на `main`; существующую метку не перемещать |
| CHANGELOG | `CHANGELOG.md`, Keep a Changelog; вверху «Не выпущено» |
| Проверки | `npm ci`, `npm test`, Python unittest, `python3 -m compileall -q container`, `git diff --check`; на Windows — сборка Docker, GPU smoke, русская запись, журнал и MCP-клиенты |
| Публикация | Есть remote, но нет CI; не объявлять версию выпущенной и не создавать тег, пока не пройдены проверки основной платформы и не определён способ публикации |

Перед выпуском убедитесь, что рабочее дерево чистое, все проверки пройдены на том же коде, а раздел CHANGELOG описывает изменения для пользователя. Обновите оба файла версии, сделайте отдельный коммит `Release {version}`, затем создайте аннотированную метку. Push, создание GitHub/GitLab Release и загрузка артефактов выполняются только по явной команде пользователя. После появления remote/CI дополните этот раздел конкретными воротами и проверяйте артефакты после публикации.
