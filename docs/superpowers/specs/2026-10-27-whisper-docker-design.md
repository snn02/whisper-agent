# Локальное распознавание проектов через Whisper

## Назначение

Пользователь просит распознавать аудио и видео в текущем проекте по запросу к Codex, Claude Code, Claude Cowork или OpenCode. Распознавание выполняется локально на NVIDIA GeForce RTX 5060 Laptop (8151 МиБ VRAM). Основная среда работы — приложения Windows; WSL также должна поддерживаться. Пользователь сам подготовит общий скил для агентов, поэтому здесь нужен устойчивый инструмент и описание его контракта.

## Требования и границы

- Использовать официальный `openai/whisper`; начальная модель — многоязычная `small`, язык — русский (`ru`), задача — транскрибация.
- Запускать GPU-контейнер для запроса и удалять его после завершения. Не держать модель и видеопамять занятыми между запросами.
- Принимать каталог текущего проекта и находить в нём поддерживаемые медиафайлы рекурсивно. Не выходить по символическим ссылкам за его пределы; пропускать служебные каталоги и каталог результатов.
- До записи результата агент проверяет правила проекта и запрос пользователя. Если путь или формат не заданы, он спрашивает их. Инструмент не принимает пустые путь и формат и не перезаписывает существующие результаты без явного разрешения.
- Сохранять полный текст только в файлах результата. В локальном журнале хранить время, имена входных файлов, длительность по файлам и всему запуску, модель, статус, пути результатов и ошибки — без текста транскрипции.
- Предоставить вызов из Windows-приложений через локальный MCP-инструмент и команду для ручного запуска. Подготовить примеры настройки Codex, Claude Code/Cowork и OpenCode для Windows и WSL. Общий скил пользователя будет обращаться к этому инструменту.
- Позволить собирать отдельные теги образов для совместимых вариантов PyTorch/CUDA. Другую модель пользователь выбирает вручную через CLI, не меняя основную установку.

Не входят в первую версию: постоянный API-сервис, облачная обработка, перевод на английский, запись с микрофона, автоматический запуск по появлению файла и установка общего скила в профили агентов.

## Рассмотренные подходы

1. **Python `venv` на Windows.** Проще запуск и меньше операций с Docker, но эксперименты с PyTorch/CUDA меняют локальное окружение или требуют нескольких `venv`.
2. **Docker-контейнер на каждый запрос — выбран.** Образы изолируют версии зависимостей и освобождают GPU после запроса. Нужны Docker Desktop с WSL 2 и корректный проброс RTX; первая сборка и загрузка модели объёмны.
3. **Постоянный контейнерный сервис.** Ускоряет повторные запросы за счёт загруженной модели, но постоянно занимает VRAM и требует отдельного сетевого интерфейса. Пользователь выбрал запуск на запрос.

## Схема

Локальный MCP-процесс на машине пользователя, запущенный вне командной песочницы агента, принимает `project_dir`, `output_dir`, `output_format`, необязательные `language` и `image_tag`. Он всегда выбирает модель `small` и отклоняет попытку передать другую модель; пользователь может вручную выбрать другую модель только в CLI. Он проверяет аргументы, показывает список кандидатов отдельным инструментом и запускает Docker с явными bind mounts: проект только для чтения, каталог результатов для записи, кэш моделей в именованном томе. Контейнер обрабатывает файлы последовательно, сохраняет результат с сохранением относительной структуры каталогов и возвращает машинно читаемую сводку. MCP-процесс добавляет запись в локальный журнал даже при неуспехе. Имена файлов и пути с пробелами/Unicode передаются аргументами процесса, без формирования shell-команды. Для работы не требуется давать самой песочнице Codex доступ к Docker socket или GPU.

Для Windows и WSL нужны отдельные тонкие точки входа к одному контейнерному обработчику; ручная команда дополнительно разрешает выбор модели. Стандартный профиль фиксирует совместимую с RTX 5060 сборку PyTorch/CUDA после проверки доступности GPU внутри Docker. Версии и теги образов фиксируются в документации, чтобы экспериментальные сборки не заменяли рабочий профиль.

Ожидаемый диалог: «распознай файлы в папке проекта» → агент находит правила и список медиафайлов → при отсутствии правил спрашивает каталог/формат сохранения → вызывает MCP-инструмент → сообщает пути результатов, длительность и ошибки. Скил задаёт этот порядок; инструмент независимо проверяет обязательные аргументы.

## Проверка результата

1. Docker Desktop на Windows уже подтвердил доступ к RTX 5060 Laptop GPU (compute capability 12.0) тестом NVIDIA `nbody`. В рабочем образе `torch.cuda.is_available()` должен вернуть `True`, а имя устройства — соответствовать RTX 5060.
2. Короткая русская запись даёт текстовый результат без перехода на CPU; контейнер после запроса отсутствует.
3. Несколько файлов, вложенные каталоги, Unicode и пробелы в путях дают отдельные результаты без коллизий.
4. Отсутствующие путь/формат, пустая папка и ошибка `ffmpeg` дают понятные ошибки; исходные файлы не меняются.
5. Журнал содержит файлы, длительность и ошибки, но не распознанный текст.
6. Инструмент виден в Codex, Claude Code/Cowork и OpenCode в локальных Windows-сеансах; вызов из WSL проверяется отдельно.

## Риски и проверки

- В текущей песочнице Codex соединение с Docker socket даёт `EPERM`, а `/dev/dxg` отсутствует. На хосте Windows Docker Desktop 4.93.0 успешно запустил NVIDIA `nbody` с `--gpus all` на RTX 5060; проблема локализована в песочнице агента. Не менять права Docker socket и не отключать песочницу ради распознавания.
- Варианты CUDA ограничены поддержкой архитектуры Blackwell в PyTorch и совместимостью с драйвером 597.01. Версия, показанная `nvidia-smi`, не означает, что любая сборка PyTorch запустится.
- Windows bind mounts могут быть медленнее WSL; кэш моделей держится в томе Docker, а не на диске проекта.
- Whisper может ошибаться на шуме и тишине. Результаты следует считать черновиком; ошибки распознавания не всегда обнаруживаются автоматически.
- Локальный MCP-процесс получает доступ к файлам проекта и Docker от имени пользователя. Он не открывает сетевой порт и ограничивает запись явно указанным каталогом результатов и журналом.

## Решения, оставленные реализации

Выбрать минимальный хостовый runtime для MCP и способ его доставки в Windows-приложения; закрепить проверенные версии образа после теста GPU; определить точный перечень расширений медиа и служебных каталогов. Эти решения не меняют пользовательский сценарий выше.
